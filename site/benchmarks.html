Benchmarks

Every speed change in ck-code and ck-code-lite starts from a profile of real build sessions: the Claude Code transcripts of builder and QA agents working on real projects. These are those measurements, before and after the release that answered them. They come from working projects, not a lab, so read them as orders of magnitude.

Finding 1

Round trips cost more than prose

The first profile covered 20 story builds and 63 QA runs on a TypeScript monorepo. Trimming the agents’ reports would have saved almost nothing. The waste was in calls and in commands run twice.

MeasuredValueWhat changed
Share of wall time spent generating60–70 %Fewer round trips per story: batched calls, inline QA folded into one run
API calls per story~75, 89 % of them single-tool turnsOne batching rule for the builder
Prose in the generated output9 %Not a lever, left alone
Test-suite runs that repeated an identical one~20 % (~62 min)7.1.0 ck-qa: one run per code state; a later step reuses a pass on the same tree
Whole-package lint piped to grep, in the inner loop60–120 s a call, up to 7× a story7.1.2 lint only the touched files
Searches of the whole disk for one fileeach hit the 120 s timeout7.1.2 never search from /
Finding 2

Run only the tests a change can reach

A story’s QA now runs the tests its diff reaches up the import chain, or up the #include chain for C and C++. A backstop then runs every area the change touches, and never an untouched one.

MeasuredBeforeAfter
Import trace on a 2,500-file monorepo15–120 s (regex only), and it picked too many tests2–7 s with exact resolution (7.15.0)
590-test C++ suite through ctest82 s serial10 s with -j 8, same 590 passing (7.23.0)
Test files a change reaches, C++ project (151 test files)all 151, every run0–37, traced in 1–14 s (7.30.0)
One story’s test run, same project1,035 s, full serial suite166–278 s for the 37 heaviest files (7.30.0)
Area backstop’s share of QA time (2,094 runs, 6 projects)3–19 %, cheap enough that it stays on every wave
Finding 3

The machine, not the model, was the bottleneck

About 600 builder and QA runs on 9 projects showed tool time overtaking model time. Parallel agents queued behind each other, and some waits never ended.

MeasuredValueWhat changed in 7.28.0
A C++ task’s time spent waiting for a CPU slot~29 of 50 minA run that barely uses the CPU starts beside the others on a half-idle machine
QA calls moved to the background by the sub-agent time cap500+, followed by 580+ polling loopsQA waits 170 s, under the 180 s cap, then an explicit wait
Machine load during waves73 median, 391 peakA 1-hour deadline per run, which stops the whole process group
Hung runs holding a slot2–8 hThe same deadline
Finding 4

Every token of instructions is paid on every call

ck-code’s builder once loaded about 80 KB of instructions for a story, against 5 KB for ck-code-lite’s. Since 7.12.0 the builder reads one short story cycle and loads the rest only when a story needs it. Since 7.31.0 the release gate flags any skill or agent file that grows more than 10 % in a release, so that growth is a decision.

Method

How these numbers were taken

Each profile reads the builder and QA agent transcripts that Claude Code saves on the developer’s machine, plus the QA logs that ck-qa writes. The projects are the author’s own working projects, named here by kind only. Quality was never traded for these gains: every story still writes a failing test first, passes an isolated QA pass and a full-area backstop, and waits for manual sign-off. Smaller or cheaper models were tried as a lever and deliberately not taken.
