ck/plugins / ck-oneshot
The first version, in one run

Docs in. A working project out.

Point it at a spec, a PRD, an architecture note, an API description or a short idea. It reads everything with parallel agents, fixes every shared contract in one blueprint, asks you once, builds in wide waves with a model chosen per unit, then checks that the project installs, typechecks, builds, lints and boots. Fast first, careful later: the tests come afterwards, in ck-code-lite.

Install ck-oneshot See how a run works
Install

Same marketplace as the others

Add the marketplace once, then install ck-oneshot.

$ /plugin marketplace add ckandrinirina/ck-code
$ /plugin install ck-oneshot@ck-marketplace

ck-oneshot is for a new project in an empty folder. It refuses an existing codebase — that is /ck-code-lite:start’s job. Run it again in the same folder to resume a run that stopped: every phase and every wave leaves a mark, and nothing finished is redone.

Use

One skill, a few flags

shot does the whole run. report files a ck-oneshot bug as a scrubbed GitHub issue, after your yes.

shot// when: a new project should exist by the end of the run

Reads every document it finds — *.md, docs/, spec/, design/, PDFs — or only the ones you name, or a one-line idea. --yes skips the one question and takes every recommendation, for headless runs. --workflow runs each wave as a resumable dynamic workflow and is offered at 20 units or more. --team lets agent teams settle an open cross-layer contract before anything is built.

$ /ck-oneshot:shot docs/prd.md docs/api.yaml
$ /ck-oneshot:shot
$ /ck-oneshot:shot "a team todo app with boards, cards and email invites"
$ /ck-oneshot:shot --yes
$ /ck-oneshot:shot --workflow
$ /ck-oneshot:shot --team
How a run works

Eight phases, one question

Intake to hand-over. The only point where the run waits for you is the gate in phase 4.

PhaseWhat happensWho
1 IntakeRefuses an existing codebase, collects the documentsorchestrator
2 DigestOne doc-reader per document, plus a researcher pinning current versions and idioms — all in one messageHaiku subagents
3 BlueprintStack, folder structure, contracts (types, schema, routes, env, props), units that each own their files, a model tier per unit, the wavesorchestrator
4 GateThe only question of the run: Proceed / Adjust / Cancel, plus real gaps in the documentsyou
5 Wave 0One agent scaffolds, installs every pinned dependency once, writes every contract and the app entryone subagent
6 WavesUp to 8 (16 with --workflow) unit-builders at once, in the same checkout, with no Bash; one verify per wave, errors routed to the owning unit’s fixerHaiku / Sonnet / Opus per unit
7 VerifyClean install, typecheck, build, lint (errors only), boot smoke, a spec-checker tracing every requirement to file:line, fix roundssubagents + ck-shot
8 Hand-overtasks/PLAN.md and docs/ARCHITECTURE.md in ck-code-lite’s format, one commit per wave, never pushedorchestrator
Why it gets few errors

Nothing left to negotiate

Parallel builders break each other in a few predictable ways. The blueprint closes each of them before the first builder starts.

Contracts are code before builders start

Builders never negotiate: every name two units share — types, schema, routes, env, props — is decided in the blueprint and written as code in wave 0.

One owner per file

Each file has exactly one owning unit. ck-shot owners refuses the blueprint otherwise, so two builders never write the same file.

Builders cannot run commands

No Bash means no half-installed dependencies and no fight over the lockfile. Builders return deps_needed and contract_requests, and the orchestrator applies them between waves.

Every error names its unit

Every verify error names a file, and every file names its unit, so a failure goes to that unit’s fixer and not to a general retry.

Models per unit

The cheapest model that can do each unit

The blueprint gives every unit a tier by difficulty, so boilerplate does not pay for a decision-maker.

TierUsed for
HaikuConfig, static pages, boilerplate
SonnetThe default
OpusUnits that must decide: auth, payments, concurrency, the foundation

A unit still failing after its fix round is retried one tier up. The cost guard holds throughout: effort never goes above high, and Fable is never dispatched without your yes.

Engines

Subagents by default, two opt-in alternatives

EngineHow it runsNeeds
defaultOne message of subagents per wavenothing extra
--workflowEach wave as the plugin’s shot-wave dynamic workflow: schema-checked verdicts, scripted retry one tier up, resumable. Offered at 20 units or morethe Workflow tool (dynamic workflows on)
--teamAgent teams settle a contract the documents leave open between two layers, before wave 0CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, which the plugin never sets for you; experimental and interactive-only

--workflow and --team are opt-in and their live runs are not yet covered by the release checks — the default engine is.

After the run

The project is already a ck-code-lite project

The hand-over is ck-code-lite’s own layout, so the next change goes through the normal workflow.

CommandWhat it does
/ck-code-lite:start <change>Plan an adjustment; no setup needed.
/ck-code-lite:build T-NNFinish a unit left doing, test first.
/ck-code:migrateMove to the full ck-code workflow; the units’ groups become epics.

Every built unit is done with a note saying it was verified by typecheck, build, lint and boot, not by tests. Wave 0 installs a test runner and one smoke test, so ck-code-lite’s test-first loop works from the first change.

Settings and compatibility

Two settings, one version floor

/plugin → ck-oneshot → configure: cost_guard (on) and update_check (on). Alongside them the plugin keeps ck-code-lite’s cost guard, writes no AI attribution into a run’s commits, and tells you when the marketplace serves a newer version.

Needs Claude Code 2.1.287 or later (mods); tested with Claude Code 2.1.330. --workflow needs the Workflow tool; --team needs agent teams.
