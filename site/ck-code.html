ck/plugins / ck-code
Spec-driven workflow plugin

Keep architecture, plan and code in lock-step.

Feed ck-code a project specification and it produces architecture docs, an epic/story plan, a per-project expert team, and a TDD build-and-ship loop — all from inside Claude Code. AI-generated code stays grounded in your real design.

The workflow

Five stages, one source of truth

Each stage hands a concrete artifact to the next. Nothing is reconstructed from memory — the spec, the docs, the plan and the code all trace back to the same place.

1

Design

Spec → per-feature architecture docs.

2

Team

Generate experts & guides for your stack.

3

Plan

Architecture → epics & sized stories.

4

Build

Implement each story with TDD + QA.

5

Ship

Commit, PR, Issues and board — through to merged.

New in 7.0

Your history holds the work, not the bookkeeping

On a real 12-epic project, 113 of 277 commits only regenerated indexes or recorded a state change. Version 7 removes that bookkeeping, fixes three bugs in the state model, and cuts the questions each story costs.

Views out of git

STORIES_INDEX.md and EPICS_INDEX.md are regenerated at every session start and on every read. They are never committed, so no state change needs a commit of its own and parallel worktrees never conflict on them.

A record per plan

Each plan carries an OVERVIEW.md with its integration level (a PR per story, per epic, or one for the plan), branch, PR and issue. plan asks the level once; build never asks it again.

A stable version stamp

tasks/VERSION.md reads layout: v7 and requires: ck-code >= 7.0.0. Updating the plugin never dirties your tree, and a teammate on an older plugin is told to update, never to migrate.

One command to repair drift

/ck-code:doctor --fix asks GitHub about every recorded PR, records work merged with no PR, moves the board cards and closes delivered issues, with or without a Projects board.

Experts that know they are stale

Each generated expert and guide records the tech stack it was written against. When the stack changes, /ck-code:doctor and the session start name the stale ones, and /ck-code:team --refresh regenerates just those.

Fewer questions, fewer retypes

ship asks once, covering files, message and PR target. fix asks nothing when given a story, and design and plan find what the previous step wrote. The hand-off chain runs from spec to published plan without a retype.

Upgrading a 6.x project takes one command. /ck-code:migrate shows the exact changes, asks once, and lands them in a single revertable commit. The conversion is a tested script, not prose the model re-derives: on a real 12-epic project it added 16 lines and removed 104. Older layouts (v3 to v5) and ck-code-lite projects upgrade with the same command.

Highlights

What's in the box

Automatic architecture docs

Split markdown in docs/architecture/ — overview, folder structure, tech stack, configuration, dev guide and _shared.md, plus one self-contained doc per feature covering its components, APIs and data.

Epic & story planning

Stories sized S/M so one agent finishes each in a pass, with explicit dependency graphs in tasks/.

TDD enforcement

Red/green/refactor cycle. No production code without a failing test first.

SOLID checks

Every implementation is reviewed against single-responsibility, open/closed, Liskov, interface-segregation and dependency-inversion.

Project-tailored experts

Auto-generated per-project expert and language-guide skills, researched via context7 for current best practices. They link your architecture docs instead of copying them, and --refresh keeps them in step with your stack.

Parallel multi-story builds

Implement unblocked stories at once in isolated git worktrees, with conflict analysis before merge. Gitignored config such as .env reaches each worktree through .worktreeinclude.

GitHub Issues integration

/ck-code:plan --publish pushes the plan, its epics or its stories to Issues in one call — labels, parent/child links, and native sub-issues that give each epic a progress bar. Re-running finishes an interrupted publish; nothing is created twice.

One source of truth, no bookkeeping commits

Story state lives only in the story file's frontmatter, and a plan's in its OVERVIEW.md record. STORIES_INDEX.md and EPICS_INDEX.md are generated views that are never committed: they regenerate at every session start, so your history holds the work, not index updates.

Delivery that follows the work

Each sync re-asks GitHub what became of every recorded PR, with or without a Projects board, so a merge you clicked in the browser lands on the story and the board with nothing running locally. /ck-code:doctor --fix repairs any drift in one pass.

Design-system fidelity

Link a claude.ai/design system and ck-code caches its tokens and component sources into the repo, then builds UI exactly against them. Fully offline after one sync.

A doctor for the project

/ck-code:doctor reports what is broken — a layout older or newer than the plugin, unparseable frontmatter, committed views, dependencies that resolve to nothing, stale experts, orphan branches, a gitignored .env parallel worktrees would lack — and names the command that fixes each one. --fix repairs the GitHub drift itself.

Capability-tier model selection

Agents pick the right Claude tier (fast / balanced / advanced) per story size — no hardcoded model IDs.

Every prompt goes through the workflow

A UserPromptSubmit hook routes each free-text prompt in an adopted project to the best-fit skill — a bug report runs /ck-code:fix, “ship it” runs /ck-code:ship, a one-off edit is still made under the project’s expert skills — announced in one line and invoked. Silent on slash commands, short replies and repos that never adopted ck-code.

Token-lean by default

Per-skill effort tuning, read-only tool hardening and dynamic context injection cut tokens and round-trips. Commands are written in the forms an optional RTK hook can filter, so a full test suite comes back as its failures alone — never required, and /ck-code:doctor reports whether it is wired. Slow suites run once per code state into a log that is read, never re-run, and the TDD inner loop runs only the story's own tests.

Delivery

“Done” is not the same as “shipped”

A story can be finished and still be nowhere near your users. ck-code tracks the two facts separately, so a board column never overstates what has actually landed on the trunk branch.

Story stateWhat it meansBoard column
in-progressBeing implemented right now.In Progress
done · no PRAcceptance criteria met, QA green — but nothing has been opened for review.Ready to Ship
done · PR openWaiting on review. The work exists, but not on the trunk.In Review
done · mergedOn the trunk branch. Genuinely shipped.Done
bugA defect was diagnosed against it — actionable work, at any stage.Bugs

Dependencies unblock on done (or skip), not on merged. Work you can build on is finished work — waiting for a merge would stall every project that reviews a whole epic at once. Set trunk_branch in tasks/SETTINGS.md when your integration branch is not the repository default, and every PR targets it automatically.

Example of use

A greenfield project, start to finish

Say you wrote a one-page spec for a task-tracking API with /ck-code:spec. Here's the whole loop; each step also offers the next one as a single question.

first run — new project
›# 1 · architecture docs from the spec
›/ck-code:design docs/specs/2026-09-24_notes/spec.md
›# 2 · experts + language guides for your stack
›/ck-code:team --standard
›# 3 · epics and sized stories (asks the integration level once)
›/ck-code:plan
›# 4 · (optional) push the plan to GitHub Issues + a Projects board
›/ck-code:plan --publish --mode stories
›/ck-code:config board
›# 5 · find the first story, then build & ship it
›/ck-code:track next
›/ck-code:build
›/ck-code:ship

After /ck-code:team, your .claude/skills/ holds expert-frontend/, expert-backend/, expert-qa/… (invoked as /expert-frontend, etc.) and guide-rust/, guide-axum/, guide-react-native/… auto-loaded when relevant files are touched — all tailored to the architecture you fed in. The folders are flat by design: Claude Code never registers a skill nested one level deeper.

When to use it

Where ck-code shines

Greenfield projects

Go from a one-page spec to a full tasks/ plan, architecture docs and a per-project expert team in a single session.

Feature additions

ck-code reads your current architecture, scopes the feature, and generates only the new epics and stories.

Disciplined AI coding

Enforce TDD and SOLID even in long autonomous sessions — the build loop won't ship untested code.

Parallel team builds

Fan unblocked stories across worktrees and let agents build in parallel, with conflict analysis before merge.

GitHub-integrated planning

Turn a story plan into a labelled, linked Issue tree with a single command, then let the Projects board track it from Todo to merged.

Up-to-date practices

Expert skills are refreshed via context7 so guidance reflects current framework docs.

Install

Add the marketplace, install, restart

$ /plugin marketplace add ckandrinirina/ck-code
$ /plugin install ck-code@ck-marketplace

Then enable it per project. Add this to the project's .claude/settings.json — without it the plugin stays dormant, keeping unrelated repos free of the workflow:

{ "enabledPlugins": { "ck-code@ck-marketplace": true } }

Requirements: Claude Code (required; built and tested against 2.1.280), gh CLI for Issue features, git for parallel builds, and context7 (recommended) for up-to-date framework docs. See the full README on GitHub for compatibility notes. Projects created by an older ck-code, 6.x included, upgrade in one step with /ck-code:migrate (see New in 7.0).
